# Shikoku 1889 Model Blueprint

Status: design brainstorm (2026-10-14). Nothing here is implemented.

1889 facts below come from the 18xx.games implementation in
`submodules/18xx/lib/engine/game/g_1889/`, base-engine defaults in
`lib/engine/game/base.rb`, and tile codes in `lib/engine/config/tile.rb`.
Check them against the published rulebook before relying on them. **Open:**
marks design questions that need more thought; **Test:** marks claims or
approximations that need measurement.

## 1. Goal and constraints

- Train an AlphaZero-style model for Shikoku 1889 (standard rules; the
  beginner variant is out of scope), reusing this repo's MCTS, self-play,
  eval server, trainer, and analysis tooling.
- The 1889 engine lives in this repo in its own packages. RSS engine behavior
  and the locked v2 baseline stay untouched: `tests/test_v2_parity.py` must
  keep passing with its existing fixture.
- 1889 supports 2-6 players; the pipeline supports 3-5. Start with 3-5.
  At 3 players there are 6 privates (Uno-Takamatsu Ferry needs 4+); 2-player
  games remove South Iyo Railway.
- The central new problem is the map. The approach: one token per hex,
  Graphormer-style relation planes for adjacency and track, and
  engine-computed **build distance** so the model does not have to learn
  pathfinding from raw connectivity.

### Why hex tokens, not connected-subgraph tokens

- The map is small: 52 hexes. Total tokens stay near 80 (Section 5), versus
  59 for RSS v3 at 5 players.
- Connected components merge and split with every tile lay, so subgraph tokens
  would have no stable identity. They would also hide the frontier geometry
  and blocking that drive tile-lay decisions.
- Abstraction still matters, but it should enter as engine-computed features
  (build distance, network summaries on corp tokens), not as token boundaries.
- Message passing reaches k hops in k layers, and the map diameter exceeds the
  trunk depth. Graphormer's answer is to supply shortest-path distance as an
  attention bias, so multi-hop structure becomes one-hop attention.

## 2. 1889 at a glance

| Element | Facts |
|---|---|
| Map | 52 hexes, flat layout. 25 revenue centers: 15 cities, 7 towns (4 ports), 3 red offboards (revenue changes at yellow/brown/diesel). Every hex holds at most one revenue center, both on the base map and on every 1889 tile. |
| Terrain | 14 mountain, 1 water, 2 water+mountain hexes, ¥80 each. Upgrading Kouchi (F9) or Kotohira (I4) also costs ¥80. Labels: K (Kouchi), T (Takamatsu), H (Kotohira). |
| Tiles | 40 tile IDs, 63 tiles in total; 27 IDs have a single copy. Colors: yellow, green, brown (no gray tiles). |
| Phases | 2, 3, 4, 5, 6, D. Green from phase 3, brown from 5. Train limit 4/4/3/2/2/2. ORs per set 1/2/2/3/3/3. Corps may buy privates in phases 3-4. The first 5-train closes privates (Uno-Takamatsu Ferry survives while player-owned). |
| Trains | 2 ×6 (¥80, rusts on 4), 3 ×5 (¥180, rusts on 6), 4 ×4 (¥300, rusts on D), 5 ×3 (¥450), 6 ×2 (¥630), D unlimited (¥1100, available on 6, ¥300 trade-in for 4/5/6). |
| Corporations | 7. Float at 50%, full capitalization. Station tokens: KU 1; AR, IR, SR, KO 2; TR, UR 3. |
| Privates | TR blocks Takamatsu (K4); MF lays the port tile; ER blocks Ohzu (C4) and lays a free green tile there when sold to a corp; SMR waives mountain costs; DR exchanges for an IR share; SIR has no ability; UTF needs 4+ players. |
| Stock | 2D market, 11 rows. Sells in blocks; no selling in the first stock round; sell-then-buy or buy-then-sell. |
| OR steps | Engine order: Bankrupt, Exchange, SpecialTrack, BuyCompany, Track (one lay or upgrade), Token, Route, Dividend (payout or withhold only), DiscardTrain, BuyTrain, BuyCompany. Track is semi-restrictive: a lay must add new track the corp can reach, or upgrade the value of a reachable city. Emergency train purchases cannot buy from other corps. |
| Start | Waterfall private auction (base default). |
| Game end | Bankruptcy ends the game immediately. A broken bank (¥7000) ends it after the current OR set. |

Game length: the two full fixture games (`public/fixtures/1889/314.json`,
3 players; `962.json`, 4 players) log 457 and 522 actions, including 174-186
passes, 40-60 tile lays, and 32-52 dividend decisions. Many passes would
auto-chain in our driver, so a self-play game is likely the same order of
magnitude as RSS rather than much longer. **Test:** measure searched decisions
per game in real self-play.

## 3. Proposed repository layout

- `g1889/`: engine package (state, static data, actions and legality,
  driver, phases, track graph, route solver, token and relation extraction).
  It follows the RSS conventions in `AGENTS.md`: raw `int16` `GameState`,
  entity APIs for mutations, legality in an actions module, sparse
  phase-local actions in the engine and MCTS, dense unified masks at the NN
  boundary.
- `g1889/data/`: static tables (hexes, terrain, tile paths and counts, upgrade
  table) produced by a generator script that reads the submodule. Check in the
  generated output along with a test that regenerating it leaves it unchanged.
- `nn/transformer-1889.py`, `token-data-1889.md`, `train_configs/1889-*.json`.
- A game-interface layer for the shared pipeline (Section 11).

## 4. Engine

### 4.1 Map and tile data

- Use the 18xx engine's flat-layout side numbering so imported tile path codes
  stay valid, and document the convention in the data module.
- A tile is a set of paths among 7 endpoints: sides 0-5 and the hex's single
  revenue node. Rotation permutes the sides. Precompute a 21-bit endpoint-pair
  mask for each (tile, rotation).
- Store raw paths, not their transitive closure. Crossing tiles (16, 19, 20)
  join no tracks, and green branch tiles (23-29, 39-47) do not let a route go
  from one branch into the other, because a route cannot reverse.
- Upgrade table: (old tile, old rotation) → legal (new tile, new rotation).
  The new tile must be the next color, keep every old path, and match the
  revenue-center type and label. **Test:** check every pair against the 18xx
  engine's upgrade check.

### 4.2 Track legality (hot path)

- A legal lay for a corp needs:
  - a hex reachable from one of its stations;
  - no private blocker or reservation on the hex;
  - a tile color the phase allows, and the tile still in supply;
  - cash for terrain (SMR discount applies);
  - the semi-restrictive rule satisfied;
  - label constraints satisfied.
- Cache each corp's connectivity graph and invalidate it on tile lays and
  token placements, the same way RSS entity APIs maintain dirty caches.
- **Test:** compare legal lay sets with the Ruby engine on every state reached
  while replaying the fixtures.

### 4.3 Route solver

- Find the maximum total revenue across the corp's trains. Routes cannot reuse
  track segments, must include a corp station, cannot pass through cities
  fully tokened by other corps, end at offboards, and stop at no more revenue
  centers than the train's number (D is unlimited). Towns count as stops
  (base 18xx behavior; verify).
- Routing is not a model decision: the engine always runs max-revenue routes.
  **Open:** confirm no 1889 situation rewards a suboptimal route; withholding
  covers the usual reasons. Human games may contain suboptimal routes, so the
  replay path must accept explicit routes even though self-play never chooses
  them.
- Performance matters. The solver runs on every corp turn in an OR. It also
  runs during feature extraction if corp tokens carry best-revenue features,
  and once per tile-lay candidate for outcome features (Section 9). Start with
  exhaustive DFS with pruning, plus a cache keyed by network hash and train
  set. **Test:** exactness against brute force and against the 18xx
  `AutoRouter` on fixture states; profile per-call cost early, because the
  candidate-feature design depends on it.

### 4.4 Rest of the game

The remaining rules: stock round, waterfall auction, market movement,
emergency money raising, bankruptcy, rusting, train limits and discards,
private abilities, and private sales to corps at ½-2× face value.

**Open:** the 18xx.games engine appears to let a corp buy any player's private
and leaves consent to the players. Self-play needs an explicit rule when the
seller is not the buying corp's president: either allow only same-player sales,
or add an accept/reject sub-phase like RSS `ACQ_OFFER`.

### 4.5 Differential testing against 18xx.games

- Replay the fixtures (`314.json`, `962.json`, and the two short `hs_*` files)
  through both engines and compare cash, shares, market positions, tiles,
  tokens, trains, and revenue after every action. Logs contain `undo` actions
  (38 in `962.json`) that must be resolved first.
- More logs can come from the local docker stack, or slowly from 18xx.games
  (it shadow-blocks IPs that fetch game JSON too often).
- The same 18xx action JSON ↔ engine action mapping later powers live play
  through `utils_18xx`.

## 5. Model inputs: tokens

| Token type | Count | Features (sketch) |
|---|---|---|
| Player | ≤5 | cash, certificate count, priority deal, net worth; shares and privates arrive as relations |
| Corporation | 7 | cash, market row/column, IPO and pool shares, floated/operated flags, remaining tokens and costs, last revenue, operating order; network summary (best route revenue now, revenue centers connected, build-distance summaries) |
| Private | 7 | value, revenue, closed flag, ability-used flags; owner as a relation |
| Hex | 52 | identity embedding; terrain cost; current tile ID embedding, rotation, color; 21-bit path mask; revenue center (type, current revenue, phase revenue table for offboards, slots, slots filled); label; blocker; upgradable-this-phase; laid-this-OR |
| Train type | 6 | remaining count, price, rust trigger, availability, trade-in |
| Global | 1 | phase, round type, OR number within the set, ORs per set, bank cash, train limit, tile supply counts |

That is about 78 tokens at 5 players.

- Revenue centers are folded into hex tokens because no 1889 hex ever holds
  more than one. **Open:** separate revenue-center tokens (+25) only if
  experiments show a need.
- A learned per-hex identity embedding plays the role `corp_id_embed` plays in
  RSS: it can absorb static map knowledge (home hexes, offboard value,
  neighborhood). That gives up transfer to other maps, which is acceptable
  while the project is 1889-only.
- **Open:** tile supply as 40 counts on the global token, or as 40 tile-type
  tokens the candidate scorer can attend to. Leaning toward counts on the
  global token plus a tile-ID embedding inside the candidate scorer.
- **Open:** trains as type tokens with a corp→type count relation (like the
  share-count planes), or as per-corp count features.

## 6. Relations

### 6.1 How relations enter the model

The mechanism is v3's. Relation planes are `(R, N, N)` uint8, with query rows
and key columns. `relation_bias_mult[layer]` is a learned `(heads × R)` table,
so every head in every layer learns its own additive attention bias per
relation. `RelationInputMixing` adds a gated, projected, weighted sum of each
relation's neighbors to each token before the trunk. Static relations are
non-persistent model buffers that never cross IPC (like
`_static_company_relations`).

Distances use **one-hot bucket planes**, not one scalar plane. Each bucket
gets its own learned bias, so "exactly 1 lay away" can differ arbitrarily from
"2 lays away", and "unreachable" (no plane) stays distinct from "far". A
scalar plane could only learn a bias linear in distance.

Planes come in both directions (e.g. corp→hex and hex→corp), as the RSS
ownership relations do, so each side can attend to the other.

### 6.2 Static relations (model buffers)

- `HEX_NEIGHBOR_0..5`: directional adjacency. Direction matters because path
  masks use absolute side indices; plane k tells a hex which neighbor sits
  across side k.
- Corp home hex.
- Private ability hexes: TR blocks K4, ER blocks C4, MF port hexes.
- Optional: geometric hex-distance buckets (2, 3, 4-5, 6+). These are cheap
  but weak, since they ignore track, terrain, and blocking.

### 6.3 Dynamic relations (IPC)

| Relation | Direction | Values |
|---|---|---|
| Track crosses shared side | hex ↔ hex | 0/1 (derivable from path masks + adjacency, but explicit makes it one hop) |
| Station token | corp ↔ hex | 0/1 |
| Build distance | corp ↔ hex | buckets: 0 (on network), 1, 2, 3+; absent if unreachable |
| On shortest build path (active corp) | hex → hex | frontier hex → target revenue-center hex (Section 8) |
| Share count | player ↔ corp | raw count (as RSS) |
| President | player ↔ corp | 0/1 |
| Private owner | player/corp ↔ private | 0/1 |
| Trains owned | corp ↔ train type | raw count (if train-type tokens are used) |

### 6.4 IPC and storage

- `MAX_ATTENTION_RELATION_EDGES` (currently 256) must grow: build distance
  alone can produce 7 × 52 = 364 records per direction. uint8 token indices
  still work while there are fewer than 256 tokens.
- Dense planes scale as R·N². At R ≈ 25 and N ≈ 80 that is about 160 KB per
  state as uint8. **Open:** check how replay stores relations and whether
  replay should keep sparse records instead.

## 7. Build distance

Build distance answers the question the model would otherwise need many layers
and lots of self-play to learn: how many tile lays separate corp C's network
from hex X? Corps normally get one lay per OR, so lays roughly equal ORs.

### 7.1 Algorithm

A small integer-weight shortest-path search over hex *sides*, not hexes,
because track geometry inside a hex matters:

- **Nodes:** each shared side between adjacent hexes, plus each hex's revenue
  node.
- **Within-hex transitions** between two endpoints of one hex cost:
  - **0:** an existing path joins them. Passing through a city every slot of
    which holds other corps' tokens is not allowed. Offboards can be entered
    but not passed through.
  - **1:** one legal lay or upgrade adds the connection while keeping every
    existing path. "Legal" means a phase color allows it, a tile is in supply,
    labels match, and no blocker applies.
  - **2:** two successive upgrades are needed (e.g. yellow, then green, for a
    junction no yellow tile offers).
  - **∞:** otherwise.
- The cost table is static per (tile, rotation, allowed color set, endpoint
  pair). Only tile supply and blockers change during the game.
- **Sources:** C's station nodes. Reachability must match the engine's rule
  for which track a corp may build from.
- **Output:** distances for every corp, every state, bucketed into the
  corp↔hex planes. Corp tokens also get summaries, such as the revenue
  reachable within 0, 1, and 2 lays.

The cost is a few hundred nodes times 7 corps, so microseconds in Cython.

Compute it for **every** corp, not only the active one:

- Track is public, so the model needs to see that an opponent is one lay from
  the last open slot in a city it cares about, and when its own lay would help
  an opponent.
- For unfloated corps, compute from the home hex as if stationed there. Par
  decisions in the stock round depend on each corp's map situation.

### 7.2 Known approximations

- Each hex transition is costed independently. Two connections in the same
  hex may need different tiles, and one route could rely on a tile another
  route rules out. The result is close to a lower bound, not exact.
- Tile supply contention across planned lays is ignored (27 tile IDs have a
  single copy, so this can matter).
- Opponents filling a city's slots before C arrives is ignored.
- Phase changes: in phase 2, connections that need green cost ∞.
  **Open:** add a second variant computed with next-phase colors, or accept
  that the model learns phase timing itself.
- Lays roughly equal ORs. Exceptions: ER's free green tile when sold, and the
  MF port tile (a player action, not a corp lay).
- Terrain cost: break ties by fewest lays, then least ¥. **Open:** carry the ¥
  cost as a scalar relation (like the share-count planes) or only in corp
  summaries.

### 7.3 Validation

- **Test:** compare the search's result with an exact minimum-lay search
  (brute-force lay sequences, depth ≤3) on random mid-game states from
  self-play and fixtures, and report how often and by how much they differ.
- **Test:** property checks. Distance never increases after C lays a tile,
  ignoring tokens placed meanwhile. Distance 0 matches the route solver's
  reachable set. A hex reported 1 lay away has a legal lay that brings it to 0.
- **Test (the main experiment):** train a baseline without the build-distance
  and shortest-path planes alongside one with them, keeping configs and seeds
  matched, and compare learning speed and strength. The premise is that raw
  connectivity leads to a long random-lay phase; check that premise rather
  than assume it.

## 8. Shortest-build-path planes

Distance tells the model that a target is close; these planes tell it *which
hex* makes progress.

- Hex h lies on a shortest build path from C to target X when
  `d(C→h) + d(h→X) == d(C→X)`.
- Emit these only for the active corp. The policy is already conditioned on
  the actor, so the planes can be hex→hex: each frontier hex (one that needs a
  lay) links to the target revenue-center hexes that laying there advances.
- Targets: revenue centers not yet connected, within 3 lays. City tokens carry
  revenue and slot features, so the model can judge how much each target
  matters; no hand-picked "important" list.
- `d(h→X)` needs one reverse search per target (at most 25 small searches).
  **Test:** profile; restrict to reachable targets if needed.
- **Open:** bucket by `d(C→X)`, or by target value, to reduce noise when
  there are many targets.

## 9. Actions and policy heads

| Decision | Choice | Readout (proposal) |
|---|---|---|
| Private auction | buy at face / bid (amount) / pass | joint scorer over bid levels, like RSS `BID` |
| Stock round | buy (corp, IPO or pool) / sell (corp, block size) / par (corp, price) / pass | candidate scorers like RSS `INVEST` and `PAR` |
| Track: hex | pass, or pick a hex | shared MLP over (actor context, hex embedding), i.e. pointer over hex tokens |
| Track: tile | (tile, rotation) at the chosen hex | candidate scorer with outcome features (below) |
| Token | pass, or pick a hex with an open reachable slot | pointer over hex tokens |
| Route | none | route solver |
| Dividend | payout / withhold | joint scorer with revenue and price-move features, like RSS `DIVIDENDS` |
| Buy train | depot (type, trade-in) / other corp (corp, train, price) / pass | candidate scorer; price uses the RSS ACQ price decomposition and caps |
| Buy private | (private, price ½-2× face) | candidate + price decomposition |
| Discard train | train type | candidate scorer |
| Emergency money | sell (corp, block) | as stock-round sell |
| Private abilities | ER green tile, MF port tile, DR exchange | reuse the tile and stock readouts |

### Tile lays

- Lays are factored as hex, then (tile, rotation). A dense hex × tile ×
  rotation space is about 12,000 slots, too large for the unified-mask
  contract. The factored version needs 52 + 240 slots.
- Outcome features for each (tile, rotation) candidate, computed by the engine:
  - the resulting path mask;
  - change in C's build distance to each target, plus a value-weighted summary;
  - revenue centers newly connected;
  - change in C's best route revenue with current trains, and with the next
    train tier;
  - change in each opponent's build distances (track is shared);
  - terrain cost;
  - remaining supply of that tile ID after the lay.

  These follow the pattern of the outcome features v3 feeds to IPO and PAR.
- **Open:** factored hex → tile versus scoring all (hex, tile, rotation)
  candidates jointly in one step. Joint scoring sees the full trade-off but
  breaks the dense unified-mask contract.
- **Open:** candidate indexing: a dense 40 × 6 tile-rotation grid (simple,
  sparse in practice) versus a compact per-hex candidate list.
- **Test:** outcome features call the route solver once per candidate, which
  could be the most expensive part of feature extraction. Profile, and fall
  back to build-distance-only features if needed.

## 10. Value and auxiliary targets

- Values stay per player in canonical order, as in RSS.
- **Open:** the terminal value definition: rank-based, net-worth margin, or a
  blend; and how a bankrupt player scores.
- **Optional auxiliary targets** (v3 has none, so this needs new replay and
  trainer plumbing), by analogy with KataGo's ownership head:
  - each corp's revenue over the next N ORs;
  - which revenue centers each corp is connected to at the end of the next
    OR set.

  These give dense supervision on map dynamics that win/loss alone teaches
  slowly. Weight them low and measure whether they help.
- **Avoid reward shaping** such as value bonuses for connection progress. It
  changes what is optimal and tends to leave artifacts in the final policy.
  Features and auxiliary targets supply information without changing the
  objective.

## 11. Pipeline: game-interface layer

- `mcts/mcts_core.pyx` is already game-agnostic. `mcts/search.py`,
  `mcts/evaluator.py`, `train/self_play.py`, `train/eval_server.py`, and
  `train/trainer.py` import RSS `core` and `entities` directly.
- A game-interface layer, chosen by config, needs to supply:
  - driver, `apply_action`, and auto-chaining;
  - sparse legal action enumeration;
  - decision phases and action sizes;
  - the unified policy layout and LUT;
  - token and relation extraction (dense and sparse);
  - static relations and layout constants;
  - the model contract.
- RSS paths must stay behaviorally identical through the refactor, with the v2
  parity test green.
- **Open:** one generic pipeline, or a 1889 fork of the pipeline modules.
  Generic costs more up front but avoids two copies drifting apart.
- Later: `train/analyze_game.py` support and 18xx.games live play for 1889.

## 12. Risks, ranked

1. **Engine correctness and speed.** Track legality, upgrades, the route
   solver, emergency money, and bankruptcy are the largest chunk of work.
   Differential replay against the Ruby engine is the main safeguard.
2. **Route-solver cost.** It sits on the OR hot path and possibly inside
   feature extraction; it decides how rich the candidate features can be.
3. **Pipeline generalization.** Refactoring the shared modules without
   disturbing RSS or v2.
4. **Build-distance fidelity.** The approximations in 7.2 could mislead early
   training. Measure the error, and let the baseline-versus-features
   experiment decide whether it pays off.
5. **Action-space design.** Tile-lay factoring, train and private price
   decomposition, and private-sale consent.
6. **Inference cost.** About 78 tokens versus 59, with more relation planes.
   Attention cost grows quadratically, and self-play cost dominates.

## 13. Suggested milestones

1. Static data generator (hexes, tiles, upgrade table), checked against the
   Ruby engine.
2. Engine core: auction, stock round, OR with track, tokens, routes,
   dividends, trains, privates, game end. Differential replay of the fixtures.
3. Route solver exactness and profiling.
4. Feature extraction: tokens, static and dynamic relations, build distance,
   and the approximation study (7.3).
5. Game-interface refactor of the pipeline (v2 parity green).
6. Model v0 without build-distance or shortest-path planes, then v1 with
   them, under matched configs.
7. Analysis tooling and 18xx.games live play.
